# 给 Codex：查询总时限过紧，可能截掉正常回答（2026-10-31，Claude 审 1.0.349 后发现，用户指定 Codex 改）

## 问题

`src/agent/lookup/clock.js`：

```
LOOKUP_TOTALS = { weather: 5000, sports_live: 10000, news: 20000, sports_news: 20000, market: 15000, general: 45000 }
```

被 `lookup/turn.js` 当作**包含模型写回答在内的硬上限**。到点时：

- 模型已在连续出字：多等最多 `WRITING_GRACE_MS`（30 秒）写完。这部分没问题。
- 模型**还没开始出字**：直接中止，用 `lookupDelivery.text()` 把原始工具输出（“先给你本轮实际取得的数据：…”），或“本轮查询未能在时限内取得可核实的结果”交给用户，并标“部分完成”。

用户服务器实测，模型首字常在 8～12 秒（10-30 截图有“首字 8.4s”“首字 11.7s”）；“今天天气”一次总共 17 秒。按现在的 5 秒 / 10 秒上限，天气和实时比分会经常拿到原始数据加“部分完成”，而不是正常回答。

方案里写的“天气首字 ≤3 秒、完成 ≤5 秒”等是**速度目标**，不是硬上限。这里是方案没写清楚，Claude 的责任。

## 要改的

1. **速度目标和硬上限分开**：
   - `LOOKUP_TARGETS`：保留现在的数字，只用于计时统计和报告（taskTiming / `evals/lookup-live.mjs` 里标“达标 / 未达标”），不触发中止。
   - `LOOKUP_TOTALS`（硬上限）放宽，防止无限等待：

     | 类型 | 硬上限 |
     |---|---|
     | 天气 | 20 秒 |
     | 实时比分 | 25 秒 |
     | 行情 | 20 秒 |
     | 新闻 / 体育资讯 | 45 秒 |
     | 一般问题 | 60 秒 |

     数字可按实测微调，但不能小于“取数上限 + 模型首字常见耗时”。
2. **取数和写回答分开计时**（推荐）：
   - 取数阶段（预取、工具调用）按较短时限收尾，到点用已取得的数据进入回答阶段；
   - 回答阶段从交给模型起单独计时；
   - 模型迟迟不出首字（比如超过 15 秒）时，才用工具数据兜底。

   兜底文本要整理成人能读的一段（天气就是“南京今天晴，11～22°C …（来源、时间）”），不是原始回执；也不要标“部分完成”，因为数据本身是完整的。
3. 原有保护保留：
   - 连续出字宽限；
   - 用户“再查”放宽；
   - 长任务 / 代码 / 画图不受查询时限截断；
   - 迟到回写取消。

## 测试（只加不删）

- 模拟模型首字 9 秒的天气问题：拿到模型的正常回答，不出现“部分完成”、不出现“先给你本轮实际取得的数据”。
- 模拟模型 20 秒仍无首字：用整理过的天气文字兜底，不是原始回执。
- 实时比分、新闻各加一条同类测试。
- 旧测试里涉及 5 秒 / 10 秒总时限的断言，按新规则补新测试；旧断言如需改，在执行记录里逐条写明理由，不能直接删。
