## 二、要做的新能力：未央像 Claude Code 一样写代码

用户原话：“想让未央实现和你一样的能力，可连接 git，写代码，运行测试，发包，合并等能力。”

### 目标（做完要能完整跑通这一圈）
用户在手机上说“把 xx 仓库里 yy 的 bug 修一下，测试过了发个 PR” →
未央在**服务器**上：拉代码 → 开分支 → 读代码 → 改 → 装依赖、跑 lint 和测试 → 修到通过 → 提交 → 推送 → 开 PR → 看 CI → CI 红了自己修 → 绿了**问用户**要不要合并 / 发版 → 用户在手机上点确认 → 合并、触发发版 → 完成后通知手机。

### 约束（必须遵守）
- 三端：主要跑在**服务器**（有 Docker）；桌面版可接本机仓库（已有 `computer_run`）；手机只做遥控和确认。App 本身不带 Python。
- 只借鉴开源。可参考 OpenHands（MIT）、Aider（Apache-2.0）的做法，按未央的写法重写，不整段复制。新依赖发布满两周；能用系统 `git` 就不加依赖。
- **令牌绝不进模型上下文、日志、对话、仓库**；只存在服务器 `config.json`（0600），模型只拿到“已连接 / 未连接”。
- 国内网络：GitHub 可能慢或断，克隆、推送要有超时和重试，并支持 Gitee / 自建 GitLab（同一套 git HTTPS + 令牌）。npm 依赖走镜像（npmmirror，可配置）。
- 不可逆或对外的操作（推送、开 PR、合并、触发发版、删除分支）**每次都要用户确认**；不许强推，不许直接推默认分支，除非用户在设置里明确允许；提交前扫一遍密钥类文件（keystore、.env、*.pem、token 字样），命中就停下报告。

### 分批（每批独立提交、补测试、写进防回退清单，按顺序做；每批先列清单和大小给用户确认）

| 批 | 内容 | 主要文件（新建为主） | 大小 |
|---|---|---|---|
| **P1 连接仓库 + 只读** | 设置里加“代码仓库”：服务商（GitHub / Gitee / GitLab）、令牌、默认分支保护开关。工具：`repo_clone`（克隆到 `数据目录/repos/<owner>__<repo>`，每个任务一个 git worktree）、`repo_status`、`repo_diff`、`code_search`（按文件名 / 内容，限量返回）、`code_read`（按行号范围） | `server/codeRepos.mjs`、`server/codeTools.mjs`、设置页一节 | 中 |
| **P2 改代码 + 沙箱跑测试** | `code_edit`（精确替换，old 必须唯一出现，和现有 edit_file 规则一致）、`code_write`；`code_run`：两段式 Docker——先 `npm ci`（只放行镜像源），再 lint / 测试（**断网、只读挂载外的目录不可写、限 CPU 内存时间**），输出截短；复用 `server/projectExecution.mjs` 的隔离做法 | `server/codeSandbox.mjs`，扩展 `projectExecution.mjs` | 中 |

| **P6 合并、发版** | `pr_merge`（需确认，默认 squash，可配置）、发版 = 触发指定工作流或打 tag（需确认）；发版后同样定时看结果并通知 | 同上 | 小 |
| **P7 写代码的“工作方式”** | 新技能包“代码开发”（照 Claude 的做法写成步骤）：先读再改；改小不改大；每次改完跑相关测试；测试失败先找原因，不删测试、不跳过；照实汇报没跑的；提交信息写清楚为什么。路由：`classifyTask` 加 `code`，能力表里给“写代码”配主力模型（Sol / Astra）；代码任务步数上限放宽（服务器现在 28 步，代码任务可到 80）和时间预算放宽；长输出用现有 `compactToolResults` 压缩 | `src/agent/skillCatalog.js`、`src/llm/router.js`、`server/taskRunner.mjs` | 小到中 |
| **P8 真实验收** | 建一个**测试用的公开小仓库**（不要用本仓库练手），完整跑：改一个故意埋的小 bug → 测试 → PR → CI → 用户手机确认合并 → 发版 → 通知。记录每步耗时和模型轮数；国内网络下 GitHub 断连、令牌失效、CI 红三种情况都要演练 | `e2e/code-agent.mjs`（用假 git 服务器 + 假 API 做可重复测试），真实演练记录写进 docs | 中 |

### 和 Claude 现有成果的衔接
- 失败步骤报错会存进回答（`failedSteps.js`），代码任务失败时用户追问能看到具体报错，不用另做。
- 云端提醒（`serverSchedules.mjs` + `notices`）直接用来轮询 CI、通知手机。
- 回答结构（`answerStyle.js` 的“交文件”“失败追问”场景）适用于代码任务汇报；需要的话加一个 `code` 场景：先说改了什么、测试结果；中间列改动文件和关键 diff；最后说没验证的部分和要用户确认的操作。

### 用户已定（2026-10-29）
- **先只接 GitHub**（Gitee / GitLab 以后再说，但 `gitHosting.mjs` 留好适配口子）。
- **第一期不合并主线、以测试为主**：第一期 = P1 连接 + 只读、P2 改代码 + 沙箱跑测试、P7 工作方式，外加 P4 里“提交并推送到**新开的工作分支**”（需手机确认，可选）。**不做 P6 合并、不做发版；不推默认分支、不开合并请求自动合并**。P3 确认卡片只为推送分支这一个操作做最小版。

- 第二期（等第一期真机验收后再定）：PR、看 CI 并修红、合并、发版。
