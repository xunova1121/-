## 最高优先级：根治 1.0.419 程序权限事故

已直接检查服务器 tar 包及构建目录：目录 `0700`，源码/前端文件 `0600`。`scripts/pack-server.mjs` 复制工作区文件时保留了构建环境的限制权限；`deploy/install.sh` 安装后将程序目录所有者设为 root，再使用 `jarvis` 账号启动，导致该账号无法读取应用。

`e2e/server-package.mjs` 的原 3 项检查用构建账号解压、启动，与文件所有者相同，因此都通过却漏掉真实部署的账号差异。这是 Codex 发布验证缺口，不能归因于用户操作或 Node 默认模型。

用户实际执行的临时恢复命令只调整程序目录：

```bash
chmod -R a+rX /opt/jarvis/app-1.0.419 && systemctl restart jarvis
```

随后用户返回：

```json
{"ok":true,"backend":"mock","model":"mock","cors":false,"mcp":false,"ollama":true,"serverMode":true,"gatewayKeys":[]}
```

其中 `backend:mock` 是默认网关状态，不证明用户保存在服务器工作区的模型 Key 丢失，也不能据此让用户重新填 Key。真实模型调用尚未测。曾有一次用户把健康检查端口复制成 87；改为 8787 后得到以上成功回执。

Claude 应补的根治：

1. 只对打包暂存的应用文件规范权限：目录可供服务账号遍历读取、普通文件可读、原本可执行的文件保留执行位，不能给其他账号写权限；不修改用户数据、配置和密钥权限，不跟随越界符号链接。
2. 安装阶段在切换 current 和重启前处理应用目录权限，并检查服务账号能读取入口及依赖；考虑启动失败自动恢复旧程序版本，避免更新失败让用户一直离线。不要把 chmod 扩大到整个 `/opt/jarvis`。
3. 保留原有 3 个安装包检查，增加严苛 umask 下的打包、归档模式检查，以及“root 安装、非文件所有者服务账号运行”的启动/页面/登录验收。仅 owner 启动通过不够。
4. 记录用户已恢复的事实，但不要把尚未实现的打包/安装/回滚改动写进“已完成”。
