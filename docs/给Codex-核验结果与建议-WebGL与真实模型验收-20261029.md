## 二、WebGL 恢复门禁（发布阻塞）：先量清，再对症，不放宽

现状：你那边 smoke 173/174，只有“WebGL 上下文丢失后恢复：未央自己 ≤ 300ms”失败（307ms）；P1 原版也复现。Claude 这台机器同一项是 `app 48ms`（`draws [14,0,0]`、`parallel false`、`simple true`），CI 最近几次也通过。所以是**慢机器上恢复路径偶尔超 7～33ms**，不是功能坏了。

### 第 1 步：量清 300ms 花在哪（不改任何门槛）
- 这一项失败时 smoke 已经打印了 `{"total","app"} · {"parallel","compile","event","draws","simple","aa"}`，**请把失败那行原样贴进记录**（之前的记录里只有 307ms，没有分解，没法判断）。
- 临时在本地（不提交）加几项计时：`resize()` 用时、restored 事件到第一帧 `draw()` 开始的间隔、三帧之间的 rAF 间隔、当时的 `fpsCap`、`stats.softwareRenderer`、`document.hidden`。
- 同一份代码连跑 20 次，记下 app 时间的中位数、第 95 百分位和最大值；你的机器和 CI 各一份。

### 第 2 步：按数据对症（都是正当的产品优化，不是放宽测试）
| 量出来是 | 原因 | 修法 |
|---|---|---|
| `draws[0]` 很大（第一帧几十到几百 ms） | 没有并行编译扩展时，第一帧同步链接着色器 | 在 restored 事件里**立刻**做一次 `renderer.compile(scene, camera)`，不等下一个 rAF；软件渲染下第一帧只画核心粒子（`simpleScene` 已有），下一帧再加星空和辉光 |
| 三帧之间间隔大（≈42ms / 33ms） | 恢复后仍受 `fpsCap`（软件渲染、eco 是 24，手机 30）限制，3 帧至少 80～125ms 再加调度 | **恢复后的头 3 帧不受 fpsCap 限制，连着画**（恢复后尽快出画面本来就是对的），之后回到原帧率 |
| restored 之后很久才开始画 | 等 `compileAsync` 或 rAF 节流 | 能同步就同步；测试页确保在前台、有焦点 |
| `resize()` 慢 | 尺寸没变也重建渲染目标 | 尺寸没变就跳过 `setSize` |

### 第 3 步：解除阻塞的标准
- 300ms / 1500ms 两个门槛**一个字不改**；你的机器连跑 20 次全部 ≤ 300ms，CI 连续 3 次通过，才算解除。
- 如果四种情况都不是、确认只是机器调度噪声（中位数远低于 300、偶尔 307），把 20 次的数据交给用户决定要不要改成“取 3 次中位数”。**这属于改测试，必须用户同意**，你和 Claude 都不能自行决定。
- 修好写进防回退清单。

## 四、追加两项小修（用户查过原因，归你的“搜索与长任务”）
用户实测：读网页时报“普通查询的 search 调用已达到预算”，同时 DeepSeek Fetch 返回 500。Claude 查过原因（没改代码）：
1. 服务商 5xx 时 `retryRead` 每次重试都扣用户的查询次数（普通查询只有搜索 6、读 4），接口一坏额度很快扣光 → **服务商自身出错的重试不扣额度**；同一服务商连续 5xx 后，几分钟内直接走下一条线路（熔断）。
2. 任一类额度用完时，整轮联网停止并沿用第一个用完的类别名，所以读网页报的是“search 已用完” → 报错写清**哪一类、为什么**（例如“DeepSeek 搜索连续 5xx，6 次搜索额度已用完，这次读网页没有执行”）。
