## 原因（Claude 读代码 + 对话判断，没看到服务器耗时日志）

1. **没有新闻专用工具**：每次由模型自己 web_search，再逐个 fetch_url 核实，轮次多；搜索一超时就白费。成功的两次靠的都是“当天汇总页”。
2. **读网页预算太紧**：`src/agent/retrievalBudget.js` 把“今日新闻”当普通查询，`read` 只有 4 次（`search` 6 次）、总时长 45 秒；两三个页面打开失败，预算就用完了。“继续”后也没放宽。
3. **查不全就交白卷**：
   - `newsDelivery.safeNewsPartial` 只保留带当日时间标注的条目，`newsCandidates` 只给链接；
   - 核实没完成时，用户得到的是“候选链接 / 没有可靠结果”，连已搜到的标题都不列。
4. **抱怨触发重查**：“发个新闻那么慢”“你在干嘛”被当成新的查询任务。
5. 21:20 那次搜索超时的具体原因，要看服务器日志：`journalctl -u jarvis | grep 任务耗时`。

## 要做的

1. **今日新闻专用工具**（名字自定，例如 `get_today_news`）：
   - 并发读取 3–4 个固定、可靠的当天汇总页，每页最多 8 秒，任何一页失败不影响其他页；
   - 候选来源：新华财经早报（cnfin.com）、央广网《国际新闻早知道》（news.cnr.cn）、东方财富财经早报 / 晚报、中新网滚动；
   - 来源地址怎么找到“当天那一期”，要先实测；
   - 程序解析出标题、日期、链接、所属栏目（国内 / 国际 / 财经 / 科技），只保留当天的条目；
   - 模型只负责挑选、合并、写成简报，不再自己逐条搜索；
   - 目标：普通“今日新闻”15–25 秒出结果；
   - 定时任务“每日重点新闻”也走这个工具。
2. **不交白卷**：
   - 汇总页拿到多少就给多少，每条标来源和发布时间；
   - 没打开原文核实的标“待核实”，不再只给链接；
   - 一条都没拿到时，才说明原因（哪个来源失败、为什么）。
3. **新闻类预算**：
   - “今日新闻 / 重点新闻 / 新闻简报”这类请求，读网页次数放到 8 次左右；
   - 用户说“继续 / 再查”时，给一轮新的预算，不沿用已经用完的。
   - 其他普通查询的预算不变。
4. **抱怨和闲问不触发检索**：
   - “怎么那么慢”“你在干嘛”“谁让你这么做的”这类短句，直接回答，不调联网工具；
   - 和现有轻量模式判定（`src/llm/router.js`）对齐，避免误伤真正的新查询。

## 不能放松的

- 不把旧闻包装成今日新闻：日期要核对，跨天的不算今天。
- 来源链接必须是真实取到的，不编。
- 已有的新闻相关测试和 `answerRequirements` 的今日新闻约束保留。
