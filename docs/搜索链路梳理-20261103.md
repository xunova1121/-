# 搜索链路梳理与第九节修复记录

审查基线4058d03，用户截图“再试试今天新闻”，联网搜索3ms冷却失败、读取今日新闻4.5秒无结果，总计33秒。

## 当前顺序

- 泛问今天新闻：lookupIntent → lookupPlan → get_today_news → 国内已实测媒体列表/RSS，国内优先，海外按近期连通与探测限制补充；校验北京时间日期、内容与分类。来源如央广、中新网、新华财经，海外BBC/卫报/半岛，路透经CNA核对转载署名。
- 点名对象的新闻：web_search。中文顺序千帆→DeepSeek→博查→免Key→Tavily；英文DeepSeek→千帆→Tavily→博查→免Key。未配置者跳过。约2.5秒错峰启动，足量返回会取消其他请求，并非全部顺序等待。
- 免Key：必应RSS及搜索网页、百度、360等，按地区/语言选；原文读取：启用DeepSeek Fetch时先它，再直接读取，再有Key的Tavily代读。
- 专用来源无结果后有有界自救：公开搜索→换词→真实链接原文；再没有结果可用明确标时间的上次成功缓存，不能冒充本次更新。
- 健康分层：新闻站点逐源状态、query_search等工具入口状态，还有引擎适配器自己的短冷却。三个连续网络失败可使入口冷却30分钟；空内容、预算、取消和重复查询不应记为断网（391已修相应误判）。

## 已复现的问题

1. lookupIntent('今天新闻')没有subject，计划get_today_news；lookupIntent('再试试今天新闻')的subject竟为“再试试”，计划web_search；“再试一次今日新闻”同样误判。“日本新闻”应继续按真实对象搜索，修复时不能破坏。
2. recoverLookup的初始label取QUERY_LABELS[intent.kind]，不取实际工具/来源。因此web_search的入口冷却也会被写成“新闻来源冷却”。这张图不能证明千帆已经被调用并失败。
3. get_today_news读取独立新闻站点，无有效条目后回退web_search，又可能碰到已冷却的通用搜索；工具卡上的名称不展示实际全部内部来源。
4. RECOVERY_SEARCH_MS虽为20秒，runLookupOperation中query_search仍有8秒外层上限；多层时限的最短者生效。普通查询还有整轮检索预算，不能把每层标称时限相加。
5. 来源解析/日期筛选后的空结果不等于网络故障。截图未展示各源HTTP/解析/筛选原因，无法判定此次每个来源具体为什么没结果。33秒不能只根据两个工具耗时归因给网络。

## 本轮实施范围

- 正式工具工厂明确标记搜索、天气、行情（日K/报价）、赛程及今日新闻为多来源入口。它们不读取旧聚合冷却来拒绝请求。查询健康接口将聚合入口显示为未整体停用，保留历史样本供诊断。保留通用单来源包装器兼容调用，不删除原有单来源冷却与测试。
- 千帆和DeepSeek及其他搜索路线各自退避：一般连接/5xx故障30秒；授权/限流独立处理，Retry-After不提前重试；同一轮失败引擎换词不重撞。DeepSeek Fetch沿用原独立3分钟保护。新Key配置生成新适配器，不被旧聚合记录拦截。
- 真连接失败、授权限流、空结果、日期/相关性筛选、普通4xx、解析、本地安全/预算拦截分开；读取旧记录时没有明确故障证据的不再续冷却。来源记录不保存错误正文、URL参数或Key。
- 中文搜索先千帆，失败或筛选后无结果继续DeepSeek；备用已有一条有效资料即可返回，不等免费源凑数量。其他搜索源继续保留，按原2.5秒错峰。每源先筛选再判断收尾，防止旧闻/年度日历挡住备用API。
- 实际搜索从恢复层到操作层统一20秒窗口，受本轮剩余时间约束；没有给整轮无限延期。日本新闻备用9秒成功和总剩余1秒停止均加测试。
- “再试试/再试一次/重新查今天新闻”不再把重试措辞当成subject；日本新闻及其重试仍按真实对象搜索。
- 进度逐来源显示尝试、有效条数、固定HTTP/超时/退避原因；不回显上游私有正文。搜索入口失败不再误写成新闻源冷却。
