> 用户原话：“这些信息查询逻辑，都重构下，乱七八糟”“直接重构，你写方案”。
> 实施方按用户后续指定（默认 Codex 开发、Claude 互审）。

## 一、为什么要重构

### 1. 用户实测的问题（2026-10-30 ～ 31，服务器在国内）

| 问法 | 结果 | 直接原因 |
|---|---|---|
| 体育资讯 / 最近体育资讯（1.0.347） | “BBC、卫报和路透（CNA 转载）都抓取失败，结果为空” | `todayNews.js`：只问体育或国际时，`focused=true` 把国内来源全部排除，只剩国外 RSS；国内服务器连不上 |
| 今日新闻（21:20、21:22） | 搜索超时；读网页次数用完；两次都没结果 | 走通用搜索 + 逐个开网页，预算按次数卡死 |
| 今天足球赛程（15:14～15:52，多次） | 两小时内未开赛列不全，状态互相矛盾，每次措辞不同 | 赛程窗口规则散在 `sportsWindow`、技能 `zbb`、模型自由发挥三处 |
| 发个新闻那么慢 | 又从头搜了 1 分 40 秒 | 抱怨识别当时只在新闻一处有 |
| 各种查询 | 回答末尾叠着“以上是一分钟内查到的”“部分完成”“不拿旧消息凑数”等多段说明 | 收尾说明有 4～5 处各自追加 |

### 2. 结构上的根子

- **判断“问的是什么”分散在 6 处以上**：
  - `newsIntent.js`（今日新闻 / 体育资讯 / 抱怨）；
  - `preSearch.js`（要不要先搜）；
  - `sportsScores.sportsPreCall`、`sportsWindow.inferSportsWindow`（赛程时段）；
  - `lookupDeadline.isQuickLookup`；
  - `src/llm/router.js` 的 `isSmallTalk`（轻量）；
  - `agent.js` 第 416～436 行再拼一遍。

  各处正则互相打架：“体育资讯”曾被当比分，现在又只走国外源。
- **“去哪取”写死在各个工具里**：`newsSources.js`、`newsFeeds.js`、`sportsZhibo8.js`、`weather.js`、`publicJson.js` 各管各的，不知道服务器在国内还是国外，连不上也不会换源。
- **时间 / 次数限制有三套**：`retrievalBudget.js`（次数 + 时长）、`lookupDeadline.js`（总时限）、`lookupWindow.js`（给收尾留时间），叠在一起难以预测。
- **收尾说明有多处**：
  - `newsDelivery.js`、`lookupDelivery.js`、`reviewOutcome.js`、`answerRequirements.js`；
  - `agent.js` 的“以上是一分钟内查到的”。
- **测试环境和用户环境网络不同**：开发 / CI 能连国外网站，用户服务器在国内；“测试全过、用户那边全挂”。

## 二、目标

1. 一个问题只走一条清楚的路：**判断 → 选源 → 取数 → 回答**，每一步只有一个模块负责。
2. **国内网络优先**：服务器在国内时，默认只用国内能稳定访问的来源；国外来源只作补充，并且连得上才用。
3. 常见查询给出速度目标（在用户服务器上量）：

   | 类型 | 首字 | 完成 |
   |---|---|---|
   | 天气 | ≤3 秒 | ≤5 秒 |
   | 实时赛程比分 | ≤5 秒 | ≤10 秒 |
   | 今日新闻 / 体育资讯 | — | ≤20 秒 |
   | 一般联网问题 | — | ≤45 秒 |

4. **不交白卷**：查到几条给几条；一条都没有时，用一句话说清哪一步失败。
5. 回答末尾**最多一句**说明，不叠加。
6. 用户自己定过的口径要固定下来，每次一致。例如：“今天比赛赛程 = 当前起两小时内的足球，进行中 + 未开赛，窗口外不提”。

## 三、新结构

```
用户原话
  │
  ▼
① 判断问的是什么   lookup/intent.js        → { kind, params, sure }
  │（不是查询：闲聊 / 抱怨 / 追问进度 → 直接回答，不联网）
  ▼
② 选源             lookup/sources.js       → 按 kind 取来源清单（国内优先 + 健康状况）
  ▼
③ 取数             lookup/runner.js        → 并发读取、统一格式、去重、记失败
  ▼
④ 回答             lookup/answer.js        → 交给模型写；统一的一句说明
公共：lookup/clock.js（唯一的时间 / 次数限制）、lookup/health.js（来源健康记录）
```

新代码放 `src/agent/lookup/` 目录（服务器和本机共用）。`agent.js` 里查询相关的拼装只保留一个入口：`runLookup()`。

### ① 判断问的是什么（`lookup/intent.js`）

- **一张规则表**，每条：`kind`、触发词、排除词、默认参数、示例问法（正例 / 反例）。表里的示例就是测试用例。
- `kind` 第一版：

  | kind | 说明 |
  |---|---|
  | `weather` | 天气 |
  | `sports_live` | 实时赛程 / 比分 / 足彩场次 |
  | `sports_news` | 体育资讯 / 转会 / 体坛动态 |
  | `news` | 今日新闻，参数带栏目：国内 / 国际 / 财经 / 科技 / 综合 |
  | `market` | 股价 / 行情 / 汇率 / 油价 / 金价 |
  | `general` | 其他需要联网的问题 |
  | `meta` | 抱怨 / 追问进度 / 闲聊 / “你在干嘛”，不联网 |

- **用户口径**：用户明确定过的说法存进记忆（偏好），判断时先查口径再套规则。第一条：“今天比赛赛程 / 足彩赛程 / 足球赛程”= `sports_live`，足球，当前起两小时，进行中 + 未开赛，窗口外不提。
- **规则拿不准**（`sure=false`）时，才调一次便宜模型做分类（限 1 秒内、只输出 kind）；超时按 `general` 处理。
- 并入这里的旧代码：
  - `newsIntent.js` 全部；
  - `preSearch.wantsPreSearch`；
  - `sportsScores.sportsPreCall`、`sportsWindow.inferSportsWindow`；
  - `lookupDeadline.isQuickLookup / lookupRequirement / COMPLEX`；
  - `agent.js` 416～436 行的判断部分。

  `router.isSmallTalk` 保留，由它调用 intent 的 `meta` 判定，两边口径一致。

### ② 选源（`lookup/sources.js` + `lookup/health.js`）

- **来源注册表**，每个来源：

  | 字段 | 含义 |
  |---|---|
  | `id` | 来源编号 |
  | `label` | 显示名 |
  | `kinds` | 适用哪些 kind / 栏目 |
  | `region` | `cn` / `global` |
  | `priority` | 优先级 |
  | `fetch` | 地址或取数函数 |
  | `parse` | 解析函数 |
  | `timeoutMs` | 默认 8000 |
  | `needsKey` | 是否需要密钥 |

- **地区**：配置项 `lookupRegion`，默认 `auto`。
  - 服务器模式下按服务器时区 / 一次连通性探测判断，手机 / 电脑本机按系统时区。
  - 设置里可手动改为“国内 / 海外”。
  - `cn` 时 `global` 来源只作补充。
- **健康记录**（`health.js`，存 kv）：
  - 每个来源记最近 10 次的成功 / 失败和耗时；
  - 连续失败 3 次就冷却 30 分钟，冷却期间跳过，用下一优先级的来源；
  - 设置里能看到各来源状态，方便排查。
- **第一版来源**（Codex 先在**国内网络**实测可用性和解析，不可用的不上）：

  | kind | 国内 | 补充（global） |
  |---|---|---|
  | weather | 和风天气（已有） | Open-Meteo（已有） |
  | sports_live | 直播吧比分（已有 `sportsZhibo8`） | — |
  | sports_news | 直播吧新闻、新浪体育、中新网体育栏目、央视体育（待实测选 2～3 个） | BBC Sport、卫报体育（已有） |
  | news 国内 / 综合 | 新华财经、央广网、中新网滚动（已有） | — |
  | news 国际 | 中新网国际、央广《国际新闻早知道》、参考消息（待实测） | BBC、卫报、半岛、CNA 转载路透（已有） |
  | news 财经 / 科技 | 新华财经、东方财富早晚报、中新网财经 / 科技（待实测） | BBC 财经 / 科技（已有） |
  | market | 现有 `stockKline`、`publicJson` 白名单 | — |
  | general | 现有 `web_search`（博查等）+ `fetch_url` / `fetch_json` | — |

- 旧代码去向：
  - `newsSources.js`、`newsFeeds.js`、`newsRss.js` 的解析器保留，挪进注册表；
  - `todayNews.js` 改成调 runner 的薄壳，工具名 `get_today_news` 不变，兼容已有定时任务。

### ③ 取数（`lookup/runner.js`）

- 按选出的来源**并发**读取，每个最多 `timeoutMs`，整体受 clock 管。
- 统一条目格式：

  ```
  { title, url, source, publishedAt, kind, category, summary?, status?, score?, verified: 'index'|'page'|'api' }
  ```

- 同链接去重；转载按原始机构去重（保留现有路透转载核对逻辑）。
- 返回 `{ items, failures: [{ source, reason }] }`，失败原因说人话：连不上 / 超时 / 解析不出 / 当天无内容。
- **先查再问模型**：`kind` 明确的（weather / sports_live / news / sports_news / market），先由 runner 取数，再把结果连同问题一起给模型，一轮写完（现在 `preSearch` 的思路，统一到这里）。
- `general` 仍由模型调 `web_search` / `fetch_url`，这些工具内部也走 runner 的并发、超时和健康记录。

### ④ 回答（`lookup/answer.js`）

- 给模型的说明只有一份（按 kind 选），替代：
  - `NEWS_LOOKUP_NOTE`、`SPORTS_NEWS_NOTE`、`WEB_LOOKUP_NOTE`；
  - `preSearchNote`；
  - 散落在 `agent.js` 的查询提示。
- **统一说明规则**：
  - items 不为空：正常写，每条带来源和时间；部分来源失败时，末尾最多一句（“BBC 连不上，以下来自直播吧和新浪体育”）。
  - items 为空：一句话说明哪一步失败，再给一个能做的下一步（换说法 / 稍后再试），不再列一串候选链接。
  - 时间到了还没写完：先交已写好的部分，末尾一句“还可以再查一会儿”。

  替代掉的收尾说明：`newsDelivery.safeNewsPartial / newsCandidates`、`lookupDelivery`、`reviewOutcome` 里查询相关的提示、`agent.js` 的“以上是一分钟内查到的”。
- `answerRequirements.js` 里的硬约束保留（今日新闻日期核对、来源要真实），只是挪到 answer 的检查里统一执行，不再另加说明。

### 公共：`lookup/clock.js`

- 合并 `retrievalBudget.js`、`lookupDeadline.js`、`lookupWindow.js`：每个 kind 一个总时限（见目标里的数字，深度调研另算）。
- 次数上限只防失控（如 search 12、read 12）；时间到了就进入 ④。
- 用户说“继续 / 再查”时，新开一轮时钟。
- `lookupModels.js`（规划用推理档）保留，由 clock 决定什么时候用。

## 四、迁移和测试规则

1. **分三步提交，每步都能发版**：
   - 第 1 步：建 `lookup/` 骨架 + intent + sources / health + runner，只接 `sports_news` 和 `news`，旧路径并存；
   - 第 2 步：接 `weather`、`sports_live`、`market`、`general`，`agent.js` 换成 `runLookup()`；
   - 第 3 步：删除被替代的旧模块和重复提示，统一说明。
2. **测试只加不删**：
   - 旧模块的导出名保留成薄壳（转调新模块），旧测试照常跑；
   - 第 3 步删旧模块时，旧测试改成测新模块的同一行为，在执行记录里逐条写明“旧测试 X → 新测试 Y，行为不变”，不能直接删。
3. **新增问法测试表**（`tests/lookupIntent.test.js`）：
   - 至少收录用户真实说过的 40 条问法和期望的 kind / 参数，例如：
     - “体育资讯”“最近体育资讯”“足彩赛程”“今天足球赛程”；
     - “今日新闻”“各三条”“国际新闻”；
     - “集团年天气”（→ weather 南京）；
     - “发个新闻那么慢”“你在干嘛”（→ meta）；
     - “gpt-sol 最便宜的中转平台”（→ general）。
   - 再加易混的反例。
4. **来源测试**：每个解析器配一份脱敏离线样例；CI 不联网。
5. **国内网络实测脚本**（新增 `evals/lookup-live.mjs`）：
   - 在用户服务器上运行（`node evals/lookup-live.mjs`），逐个来源测连通、耗时、解析条数，再跑问法表里 15 条代表问题；
   - 输出报告（kind 判对没有、用时、条数、失败原因），报告不提交仓库；
   - **发版前必须由用户在服务器上跑一次并贴结果**，不能只在开发环境通过。
6. 照常：动手前拉最新代码；不整文件覆盖；提交带 `[skip ci]`；发版前单独提交运行时固定清单；修好的问题写进 `docs/已修问题清单-不许回退.md`。

## 五、不能放松的

- 来源和链接必须真实取到；不把旧闻当今日；不编比分、赔率、编号。
- 评测隔离、代码工具隔离不受影响。
- 天气、赛程卡、新闻的现有界面展示不倒退（卡片照常出现）。
- 架构图、文档生成等非查询功能不动。

## 六、验收

1. 单元测试、lint、build、smoke、standalone 全过。
2. 用户服务器上 `evals/lookup-live.mjs` 结果：
   - 问法 kind 判对率 ≥ 95%；
   - 每类速度达到第二节目标；
   - 体育资讯、国际新闻在国内网络下能出 ≥ 5 条。
3. 发版后跑一轮 30 题，`--previous=` 对比第三轮：联网题通过率不降，耗时下降。
4. 用户实际问一遍：今日新闻、体育资讯、足彩赛程、今天天气、一个一般问题。
