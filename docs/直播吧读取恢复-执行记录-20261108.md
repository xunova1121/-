## 证据与原因

11月8日开发环境通过公开网址和实际 `publicFetch` 调用链复现；没有连接用户服务器，也没有请求模型：

- 比分 `https://bifen4pc.qiumibao.com/json/list.htm` HTTP 200，旧解析器能读出216条各项目比赛；赛程页 HTTP 200，旧解析器能读出78条计划对阵；新闻索引也可读，未发现接口字段整体更换。
- 同一环境实际调用曾出现比分6秒超时、备用页4秒超时；随后的请求又成功。因此本次证据支持间歇性慢请求，不支持“直播吧永久失效”。不能据此认定用户服务器网络完全相同。
- 比分6秒、备用页4秒、外层12秒/15秒各自计时；统一恢复还会再给整条链2秒重跑，可能浪费请求且再度超时。
- 两来源的403/404和返回格式异常都被覆盖为 `SPORTS_UNAVAILABLE kind=network`，无法定位原始问题。
- 新闻来源声明8秒，读取器却强制最多5秒；请求本身又只给3秒/重试1.5秒。一次真实DNS及请求变慢即可耗尽。
- 当前代码中赛程/搜索入口已经不受旧聚合健康记录停用，本次没有清空健康记录或重新引入入口冷却。

## 修复

- `sportsRequest.js` 统一14秒取数预算；比分请求最多8秒，备用页最多5秒，预留备用时间；重试也从同一预算扣。预取、工具包装、卡片刷新统一15秒外层，留1秒记录与交接，40秒整轮预算不变。
- 明确网络类型、底层连接错误、超时、408或5xx可在剩余额度内重试，全链最多一次；裸TypeError不能证明是连接故障，直接换源。403/404/429、解析和空范围不原源重试。遵守Retry-After，不够时间则换源；每次实际请求前扣读取额度。
- 两条国内源仍失败后进入原有 `web_search`，使用用户已配置引擎，保留球队及原始问题。取消与预算信号向上传递，不进入后备；晚到响应不再发正文请求、不更新缓存或卡片。
- 来源诊断只含固定来源标签、请求/正文/解析/范围阶段、HTTP状态、已知错误码、毫秒数，贯穿进度、健康记录和恢复失败回执。没有URL参数、Key或上游错误正文。
- 新闻列表与正文遵守来源声明预算（最高8秒）及本轮剩余额度；单请求含正文最多5秒，唯一一次重试最多2.5秒，仍共用来源预算。请求次数和来源选择规则保留，不将候选来源标记为国内已验收。
- 保留部分比赛、北京时间、所选球队、原状态和30秒缓存。计划赛程没有核实的比分/状态仍明确标注；未恢复ESPN。
